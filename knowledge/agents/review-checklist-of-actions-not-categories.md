# レビューエージェントに渡すのはカテゴリの観点表ではなく差分の外を参照する動作にするとよいはず

## 思いつき

レビューエージェントに何を渡すか、を「観点表を作り込む」方向で考えていた。
だが 187 件の PR レビューを分類した公開記事 (sources の 1 本目) の数字を見ると、力を入れる先が違うかもしれない。

| 指標 | 値 |
|---|---|
| 指摘のうちバグ | 20% |
| まだ壊れていない箇所への指摘 | 約 33% |
| 差分の外を見た結果として出た指摘 | 69% |

差分だけを読んで出せるのは 31% しかない。記事が挙げる費用対効果の高い習慣も、
根拠の保存・対の非対称・二重定義・デッドコード・silent failure・変更の波及の 6 つで、
どれも「呼び出し元を grep する」「対になる実装を並べる」「参照を数える」という**動作**になっている。

つまり効かなさそうなのは観点表そのものではなく、**カテゴリで切った観点表**の方。
null チェック・境界値・例外処理のような分類の一覧は、モデルが既に持っているものを繰り返しているだけで、
しかもそれで拾える範囲はバグの 20% 側に寄る。渡すなら観点表ではなく動作表になる。

## 渡すもの・渡さないもの

| 渡すか | 中身 | 理由 |
|---|---|---|
| 渡さない | 一般的なバグ分類 (null、境界値、例外) | モデルが既に持っている。書いても情報が増えない |
| 渡す | リポジトリ固有の規約と過去の事故 | コードを読んでも推測できない。外から与えるしかない |
| 渡す | 差分の外を参照する動作 | 69% がここから出る。指示が無いと差分の中で完結してしまう |

[敵対的レビューは独立コンテキストの読み取り専用サブエージェントに切り出すべき](adversarial-review-in-isolated-subagent.md)
では「マージ済みの観点表を渡す」を手順に入れているが、そこで観点表が要るとされている理由は
計画の粒度・決定記録の二重管理といったリポジトリ固有の落とし穴で、この表の 2 行目にあたる。
1 行目を削り 3 行目を足す、という差分になる。

## エージェント側の事情

差分の外を見る作業は、人間とエージェントで費用が違う。

- **grep が安い。** 呼び出し元を数える、同名の定義を探す、対になる実装を開く。人間には「もう 1 枚開く」判断が要るが、エージェントには単なるツール呼び出し
- **疲れない。** 5 ファイル目でも 1 ファイル目と同じ密度で読む
- **足りないのは動機。** 差分を渡されたら差分の中で答えを出そうとする。外を見ろと明示しない限り 31% の側に留まる

実力差の正体が「もう 1 枚ファイルを開くかどうか」なら、その差が一番埋まりやすいのがエージェント側になる。
逆に言うと、ここを指示しないのが一番もったいない。

## 「保守性」を動作に落とす

保守性を見ろ、とだけ渡すと自由文の講評になる。だが中身を分けると 2 つに割れて、片方は既に動作になっている。

1. **他機能と実装方法が違って認知しづらくないか** → 他機能を開いて並べないと言えない。記事の 対の非対称 と 二重定義 と同じ動作に潰れる
2. **行数を削るために難しく書いていないか** → 隣を見ても答えが出ない。比較対象が repo の中に無いので、エージェントは自分の「読みやすいコード」の事前分布に落ちる

2 つ目に参照点を与える方法は 2 つ考えられる。

- **repo の平均に当てる。** 同じ種類の処理がこの repo でどう書かれているかを先に読ませ、そこから外れているかを言わせる。参照先が「対になる実装」ではなく「同種の処理全般」になるだけで、動作としては 1 つ目と同じ形
- **書き直しテスト。** 素直な版を実際に書かせて比較させる。素直版が数行しか増えないなら凝った側が負ける、明確に長くなるなら凝った側に理由がある

書き直しテストの方が筋がよさそう。エージェントは書くのが安いので、人間のレビュアーには重すぎるこの手が使える。
指摘も「素直に書くとこうなる、差はこれだけ」という比較可能な形になり、反論できる。

## failure_scenario の必須条件と衝突する

[レビューエージェントは判定せず確度と重大度を付けた findings を返し、閾値と投稿は呼び出し側が持つべき](reviewer-scores-findings-caller-applies-threshold.md)
では、この入力でこう壊れるというシナリオを必須にし、書けない指摘は感想だとして確度に反映させていた。
だが記事の数字では約 3 分の 1 が「まだ壊れていない箇所」への指摘で、認知しやすさの指摘は全部そこに入る。
実行時の失敗に限定すると、価値の 3 分の 1 を仕組みで削ることになる。

そこで失敗の主体をプログラムに限定せず、**誤読シナリオ**を同格で認める形に緩めた。
「次にこのファイルを触る人は X だと思って Y を足す、実際は Z なので壊れる」まで書ければ、感想との線引きは保てる。
具体性の要求は同じ強さで掛かるので、必須条件を外したわけではない。

## 確かめていないこと

- **この形で走らせていない。** 動作表を渡したレビュアーと、カテゴリの観点表を渡したレビュアーで、指摘の質と件数を比べていない
- **数字は他者の計測。** 187 件は人間による PR レビューの分類で、エージェントのレビューで同じ比率になる保証は無い。特に 20% という値は、エージェントが差分内のバグを拾いやすい分だけ上振れしうる
- **動作を指示すると本当に外を見るか分からない。** 「呼び出し元を grep せよ」と書いても、差分で答えが出たと判断して省く可能性がある。動作を実行した証跡 (どのファイルを開いたか) を findings に含めさせないと、やったかどうか区別できない
- **書き直しテストのコストが見合うか分からない。** 指摘候補ごとに素直版を書かせるとトークンが増える。全行に掛けるのは無理なので、どこで発動させるかの条件が要る
- **誤読シナリオが作文を招かないか分からない。** 実行時の失敗より書きやすいので、確度の低い指摘が通りやすくなる方向に働く可能性がある

## 昇格の目安

(.claude/rules/knowledge-authoring.md「note を昇格させる」)。満たしたら type を変える。ファイルは動かさない。

- [ ] 粒度が type の定義に収まっている → 「課題と解決」の形なので `pattern` になる見込み
- [ ] sources に一次情報がある → 記事は計測を含むが二次情報。エージェント側で自分の計測を取れると強い
- [ ] 実際に試して applies_to と verified_at を書ける → 同じ diff に 2 種類の指示でレビューを掛けて比べる
