# .claude/docs の書き方 (要件と仕様)

このリポジトリ自身の道具 (skill・スクリプト・`pnpm` コマンド) の説明を置く。汎用のエージェント開発知見は knowledge/ に書く。
1 つの道具につき `00_requirement/<slug>.md` と `10_spec/<slug>.md` の 2 本を作り、必ず相互にリンクする。slug は両方で揃える。

## 一番大事な境界

**requirement には外から観測できることだけを書く。内部のことは 1 行も書かない。**

書いているうちに理由や仕組みを説明したくなるが、そこが混ざると要件が実装に固定され、実装を変えるたびに要件が嘘になる。
迷ったら「利用者がこの道具の中身を一切知らなくても、この文が正しいか判定できるか」を問う。判定できないなら spec に移す。

| 観点 | requirement | spec |
|---|---|---|
| 入口のコマンドと引数 | 書く | 書く |
| 入力に何を受け付け、出力に何が出るか | 書く | 書く |
| 成功・失敗の判定、終了コード、利用者に見えるメッセージ | 書く | 書く |
| 出力物が満たす性質 (書式、置き場所、辿れること) | 書く | 書く |
| 外部通信の有無 | 書く | 書く |
| やらないこと (適用範囲外) | 書く | — |
| **実装言語・ライブラリの選定理由** | **書かない** | 書く |
| **依存の導入方法、実行環境の用意** | **書かない** | 書く |
| **処理の順序、走査方法、正規表現、定数値** | **書かない** | 書く |
| **子プロセスの起動方法、内部で呼ぶコマンド** | **書かない** | 書く |
| **作業手順 (どう作るか)** | **書かない** | 書く |

判定に迷いやすい例。

- 「Node ではなく Python を選んだ理由」 → 内部。spec の「設計判断」へ
- 「Python 本体は uv が用意する」 → 内部。spec の「前提」へ
- 「出力ブックは数式を含まない」 → 外部。requirement に残す
- 「openpyxl が数式の値をキャッシュしないから」 → 内部。spec の「設計判断」へ
- 「npx を経由せず直接実行する」 → 内部。spec へ
- 「生成 HTML から元の markdown を辿れる」 → 外部。requirement に残す

## 00_requirement の構成

```
# <道具> の要件
（1 行で spec へのリンクと「ここには外から観測できることだけを書く」の断り）

## 背景        何が困っていたか。1〜2 段落
## 外部要求 (EARS)   ID・型・要求の表
## ハッピーパス      mermaid
## 適用範囲外        できないこと、やらないこと
## 受け入れ条件      外から確認できる合格条件
```

**外部要求は EARS 形式で書く。** ID は `REQ-<3 文字>-<連番>`。型は次の 5 つから選ぶ。

| 型 | 書き方 |
|---|---|
| ユビキタス | 〜は、…すること |
| イベント駆動 | …したとき、〜は、…すること |
| 状態駆動 | …の間、〜は、…すること |
| 望ましくない挙動 | もし…ならば、〜は、…すること |
| オプション | …する場合、〜は、…すること |

主語は道具の名前 (「xlsx 生成は」)。曖昧語 (適切に、必要に応じて、高速に) は使わない。1 要求 1 文。

**ハッピーパスは mermaid で描く。** 成功する筋道だけを描き、エラー分岐は書かない (それは「望ましくない挙動」の要求が担う)。
1 枚あたり 4〜6 ノードに収め、超えるなら工程で切って複数枚にする。1 枚に全部詰めない。

## 10_spec の構成

```
# <道具> の仕様
（1 行で requirement へのリンク）

## 前提            必要な環境と導入
## 外部インタフェース  コマンドライン、引数の表
## 内部の挙動        処理の順序を番号付きで。判定条件と定数も書く
## 設計判断          なぜその実装にしたか
## 手順             利用者の操作
## 確認方法          動いたと分かる見方
## つまずきどころ     実際に踏んだもの
```

実装ファイルを `sources` に相対パスで入れる。実装を変えたら spec も同じコミットで直す。

## frontmatter

`.claude/` は lint と index の対象外なので taxonomy.yml の語彙は使わない。`type` は `requirement` か `spec`。
それ以外のキー (`title` `description` `status` `verified_at` `applies_to` `sources`) は knowledge と同じ書き方に揃える。`description` は英語で What / Use when / Not for を書く。

`superseded_by` と `derived_from` は `.claude/docs/` の ID を指してよい。lint はファイルの実在を見る。
